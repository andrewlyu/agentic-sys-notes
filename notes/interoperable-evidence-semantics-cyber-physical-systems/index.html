Interoperable Evidence Semantics for Distributed Cyber-Physical Systems: Applying CloudEvents, SOSA/SSN, and W3C PROV

Distributed cyber-physical systems can exchange messages successfully and still disagree about what those messages mean. A receiving system may recognize an identifier and timestamp yet remain unable to tell what was observed, which physical property the result describes, or how a later conclusion was derived.

That gap matters wherever software decisions depend on evidence from the physical world: manufacturing, energy, transportation, buildings, environmental monitoring, and connected medical equipment. The NIST Cyber-Physical Systems Framework treats interoperability as a cross-domain concern because these systems combine computational, communication, and physical capabilities across organizational and technical boundaries.

A practical response is to use established standards in layers. CloudEvents can identify and carry an event. SOSA/SSN can express what an observation means. W3C PROV can describe how evidence was produced or derived. Each answers a different question; none is a complete data model by itself.

Exchange is not the same as shared meaning

Two systems can agree on JSON, a message broker, and a timestamp format while assigning different meanings to the same data. One may treat a time as the moment a physical phenomenon occurred; another may treat it as the moment a result entered a database. Both messages are syntactically valid, but their interpretations conflict.

Interoperability therefore has layers. Transport and serialization make data movable. Event context makes records identifiable and routable. Domain semantics make observations interpretable. Provenance makes transformations and dependencies inspectable.

The goal is not to merge three standards into a new universal ontology. It is to give each standard a clear responsibility and define the mappings between them.

CloudEvents: portable event identity and context

CloudEvents 1.0.2 defines a vendor-neutral format for event data. It separates event context—such as source, identifier, type, and optional occurrence time—from the domain-specific payload. That division lets generic infrastructure route, filter, and inspect an event without understanding every payload schema.

Its identity rule is deliberately scoped: the combination of source and id identifies a distinct event. An id is not assumed to be globally unique on its own. This supports independent producers while giving consumers a stable pair for duplicate detection.

CloudEvents does not define what a temperature reading, machine state, clinical measurement, or traffic observation means. It standardizes the event envelope, not the domain semantics inside it. Its graduation within the Cloud Native Computing Foundation in 2024 reflects its maturity as an interoperable event format, but does not change that boundary (CNCF, 2024).

SOSA/SSN: the semantics of an observation

The W3C Semantic Sensor Network ontology, 2023 Edition supplies a domain-neutral vocabulary for sensors, observations, samples, and actuations. Its lightweight SOSA core makes several distinctions that an event envelope cannot:

  • the observation is the act that produced a result;
  • the feature of interest is the thing whose property is being examined;
  • the observable property states what characteristic is being measured;
  • the procedure describes how the observation was made;
  • the result records the outcome; and
  • phenomenon time and result time distinguish when the observed condition applied from when the result became available.

Those concepts travel well across domains. A vibration reading from industrial equipment, a voltage measurement in a power network, and an air-quality sample can use the same observation pattern while retaining their own domain vocabularies.

SOSA/SSN provides a semantic frame, not a transport guarantee. It does not decide how messages are retried, how clocks are synchronized, or whether a claimed observation is trustworthy.

W3C PROV: evidence lineage

W3C PROV-DM describes provenance through entities, activities, agents, and relations among them. In practical terms, it can represent a source observation as an entity, a calibration or aggregation step as an activity, and a responsible system or organization as an agent.

PROV also distinguishes generation from derivation. An entity can be generated by an activity and derived from an earlier entity. This lets a consumer ask whether a report came directly from an instrument, from a transformed dataset, or from a chain of analytical steps.

Lineage is evidence about origin and transformation. It is not proof that a value is true, a procedure is correct, or an actor was authorized. Those judgments require validation, policy, and controls outside the provenance graph.

How the layers compose

The three standards form a useful separation of concerns:

  1. CloudEvents answers: Which event record is this, where did it originate, and what event category does it carry?
  2. SOSA/SSN answers: What was observed, which property and feature were involved, how was the observation made, and what result was produced?
  3. W3C PROV answers: Which activities and agents produced or transformed the evidence, and which earlier entities contributed to it?

A receiving system can first use CloudEvents context to handle and deduplicate a record. It can then interpret an observation using SOSA/SSN concepts. If the result was calibrated, aggregated, or incorporated into a later report, PROV can preserve that lineage.

This composition is intentionally loose. CloudEvents need not become an ontology. SOSA/SSN need not become a message envelope. PROV need not redefine the observed property. Stable mappings between the layers are more valuable than collapsing their responsibilities.

What an implementation must still define

Standards reuse narrows the design space; it does not remove design work. An implementation profile still needs explicit rules for:

  • identity scope and lifecycle, including what constitutes a new event;
  • duplicate delivery, replay, and out-of-order arrival;
  • clock uncertainty and the meaning of every time value;
  • missing, partial, contradictory, or late evidence;
  • integrity protection and verification of transformations;
  • vocabulary governance and versioning; and
  • access boundaries for sensitive observations and provenance.

Recent NIST work on agile manufacturing data standards illustrates why this remains an active engineering concern: networked cyber-physical components need standards that can support interoperable information exchange as systems evolve.

These choices should be testable. For example, a profile should say whether retransmission preserves event identity, how uncertainty accompanies a time estimate, and what happens when lineage is incomplete. The standards provide vocabulary and structure; the profile supplies operational rules.

This composition describes standards-aligned design. Demonstrating conformance requires a named profile, normative mappings, and test evidence—a separate subject deserving its own treatment.

A reusable pattern across domains

The layered pattern applies wherever evidence crosses system boundaries:

  • an industrial controller emits a portable event describing an equipment observation, followed by a calibrated result with preserved lineage;
  • an energy platform exchanges measurements from independently operated assets while retaining the meaning and origin of each result;
  • a transportation system relates infrastructure observations to derived operational assessments; or
  • an environmental network combines samples from different procedures without erasing how each result was obtained.

This pattern applies wherever evidence must move between independently designed systems while preserving its meaning and lineage.

CloudEvents, SOSA/SSN, and W3C PROV provide credible building blocks for that purpose. Their value comes from disciplined composition: one layer for event context, one for observation semantics, and one for provenance—joined by an explicit implementation profile and described with claims no broader than the evidence supports.
