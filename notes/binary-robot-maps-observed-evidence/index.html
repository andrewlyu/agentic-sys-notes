Exploring a Robot’s Binary Map in Simulation

This experiment uses a public robot-vacuum map as a hidden environment for a virtual robot to explore.

Dashboard highlight: After 60 simulated seconds, the dashboard shows the robot’s position, traveled path and discovered floor and walls. Blank areas remain unknown. This screenshot records the local simulation with accelerated time.

Instead of inventing a floor plan, I use an existing robot map to build the simulated environment. A software simulation moves a robot through that environment, choosing where to go from simulated sensor observations. The dashboard shows its position, traveled path and growing discovered map. The next extension is to introduce sensor incidents and watch how that picture changes.

From a binary file to a virtual environment

I use the public roboroommap-with-objects.rrmap sample from the community-maintained XiaomiRobotVacuumProtocol repository. It uses the vendor-specific RRMap format associated with Roborock robot vacuums, rather than a general robotics map standard.

The map arrives as a binary file, so its bytes need an interpretation before the simulator can use them. Community research on the RRMap format provides that interpretation. This is where reverse engineering enters the experiment: working out how the file represents the map. My prototype applies that existing knowledge to decode the geometry and build a grid of free, occupied and unknown cells; it does not claim a new format discovery.

The sample is not from my robot or home, and its original hardware provenance is unverified. For now, it supplies a recorded environment that can be loaded repeatedly without robot hardware.

Here, the virtual robot is a software model with a position, a simulated range sensor and an exploration rule. At each step it chooses a move through discovered free cells, returning through known space when it needs to explore elsewhere. The path emerges during the simulation; it is not a playback of the route recorded in the sample file.

I decode the binary map into a hidden floor plan. At each robot position, a simulated range sensor checks nearby space along virtual rays, revealing floor and walls within its range. These observations gradually build the map shown on the dashboard.

Only the simulated sensor reads the complete floor plan; the explorer receives the discovered map. The observations are generated from the recorded map, not captured from a real sensor. That separation lets me observe how the robot's view of an existing environment gradually emerges.

Watching the map take shape

The dashboard displays the simulation's current state: the robot's position, its traveled path, and the free and occupied cells accumulated from simulated observations. It also reports elapsed simulated time and observed-cell count. At the start, the discovered map is blank. As the robot moves and senses nearby space, floor and walls appear; unobserved space stays unknown. This view shows simulated exploration, while data-pipeline throughput and delivery performance remain outside the experiment's measurements.

The next experiment: interrupted observations

Today’s observations are ideal. The next experiment would disturb them: a missing update, a delayed observation, conflicting map information or an obstacle that the sensor misses. The point is to see what happens to the discovered map and the small behavior that depends on it.

For example, if a nearby cell becomes occupied or remains unknown, does the system preserve that information, or accidentally treat the cell as free? A limited move-or-hold response would make the consequence visible. The experiment stays focused on map information and its effect, rather than attempting a complete model of robot control.

The intended output is a replayable incident with the map changes, observed response and comparison against the expected result. That incident workflow is not implemented yet. The existing prototype passed 53 local workflow tests across parsing, mapping, simulation, API and dashboard behavior; that count does not include the proposed end-to-end incident suite.

A missed obstacle would be particularly revealing. The system could follow its received map correctly while that map misrepresents the hidden environment. The simulator could expose that discrepancy without giving the explorer access to the hidden floor plan.

Bringing real sensor data into the experiment

A later extension would investigate the robot’s sensor communication. Reverse engineering that communication could let me capture real observations and decode or construct maps for this same simulator. The stream may contain raw sensor readings rather than a ready-made binary map; access and format still need verification.

That would connect the current dataset-based experiment with real device data. It would also give me another source against which to question the interpretation. Agreement with a simulator built from my own assumptions would not, by itself, establish agreement with the device.

For now, the implemented result is binary-map import and live simulated discovery. The sensor uses known poses and ideal range observations. Real sensor capture, incident injection and independent device comparisons remain future work; physical robot safety has not been established.

This experiment continues recent project work on data representation, information boundaries and validation. Here those concerns meet in one concrete object: a robot map that can be decoded, explored and eventually challenged with imperfect observations.
