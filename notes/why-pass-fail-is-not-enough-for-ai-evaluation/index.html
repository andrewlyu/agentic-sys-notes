Why Pass/Fail Is Not Enough for AI Evaluation

A single pass rate looks decisive. But it can hide three very different events: the AI behaved incorrectly, the evaluation itself broke, or the available evidence could not support a decision. Treating all three as “fail” produces a clean number and a bad decision.

The practical fix is to separate the system's behavior from the evaluator's ability to judge it.

This distinction is not unique to this proposal. In formal neural-network robustness verification, MathWorks distinguishes among verified, violated, and unproven results. Its vocabulary is narrower than the four outcomes proposed here, but it supports the underlying principle: an evaluation that cannot establish a conclusion should not automatically be recorded as a failure.

Four outcomes answer two questions

An evaluation first asks whether the run is trustworthy enough to produce a verdict. If it is, the evaluation asks whether the system met the criterion.

That yields four useful outcomes:

  • Pass: a valid evaluation found that the system met the criterion.
  • Fail: a valid evaluation found that the system did not meet the criterion.
  • Invalid: the evaluation cannot support a verdict because its own prerequisites, execution, or evidence integrity failed.
  • Indeterminate: the evaluation was valid, but the allowed evidence did not establish whether the criterion was met.

The matrix below makes the separation explicit: validity determines whether any verdict can be trusted; evidence determines whether a valid evaluation can decide between pass and fail.

The names are less important than the separation. A model failure, a broken test, and an undecidable question should not become the same data point.

Invalid is about the evaluation

Suppose an AI system must summarize an incident from an approved evidence bundle. During one run, the evaluation harness's input-assembly step omits a required record because its fixture is corrupted. The summary misses the record's fact.

Calling that run a failure blames the AI for evidence it never received. Calling it a pass is worse. The run is invalid because the evaluation did not satisfy its own prerequisites. The right response is to repair or rerun the evaluation path, not to update the model's quality score.

Invalid does not mean “the answer was bad.” It means the evaluation cannot responsibly say whether the answer was good or bad.

Indeterminate is about the available evidence

Now suppose the evidence bundle is complete and the evaluation runs correctly, but two authorized records conflict. Neither source has priority, and no additional evidence is allowed.

The result is indeterminate. The evaluator is healthy; the question is not answerable from the evidence. Forcing a pass or fail would manufacture certainty.

This distinction is especially important when AI systems are expected to preserve uncertainty. If an evaluation punishes an answer for refusing to resolve unsupported ambiguity, it can train teams—and eventually models—to sound certain when the evidence is not.

Established testing vocabularies already go beyond binary

The exact four terms above are a practical vocabulary, not a universal industry standard. But the underlying principle has strong precedent.

ETSI's standardized TTCN-3 testing language uses verdicts including pass, fail, and inconc for an inconclusive result. Its documentation explains that inconc can apply when the system under test does nothing illegal but the test encounters a situation it was not designed to handle. That is materially different from failure. See the ETSI TTCN-3 standards and its general-purpose test-system documentation.

The W3C's Evaluation and Report Language (EARL) 1.0 Schema likewise defines passed, failed, cantTell, inapplicable, and untested. cantTell records that it is unclear whether the subject passed or failed. EARL is a W3C Working Group Note, not a Recommendation, but it is another reputable example of preserving more meaning than a Boolean. See the W3C EARL 1.0 Schema.

Neither source standardizes this exact four-state model. They support the narrower conclusion that serious test-result vocabularies often need outcomes beyond pass and fail.

Why the distinction changes decisions

Separating outcomes keeps the response aligned with the problem:

  • A fail directs attention to the evaluated system.
  • An invalid run directs attention to the evaluation machinery or inputs.
  • An indeterminate result directs attention to evidence limits, criteria, or a qualified judgment step.
  • A pass remains meaningful because unusable runs were not silently folded into the denominator.

This also makes evaluation reports harder to game. Keeping invalid runs visible prevents a system from benefiting when broken evaluations are excluded, and it avoids penalizing honest uncertainty that the evidence cannot resolve.

Pass/fail is still useful after validity and decidability are established. It is simply not sufficient as the entire result model.

The durable rule is straightforward: do not call the system wrong when the test was unusable, and do not claim certainty when valid evidence could not decide.
