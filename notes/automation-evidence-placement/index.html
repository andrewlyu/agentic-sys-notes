Where Should Automation Evidence Live?

Automation needs telemetry to explain what happened. It may also need an authoritative record before taking a governed action. Treating them as the same thing gives logging infrastructure authority it should not have.

The separation is straightforward:

  • Observability reports behavior through traces, metrics, and logs.
  • An evidence service commits a bounded record and returns a verifiable receipt.
  • A controller applies policy to decide what the receipt permits.

A receipt proves that a record was accepted under a declared contract—not that it is true or that the next action is safe.

Three places for the evidence boundary

There are three common placements, and each makes a different tradeoff.

A. An in-process evidence service

The controller calls a separate evidence module in the same process. This creates a logical boundary at low operating cost, but not an independent security or availability boundary.

B. One transaction for business state and evidence

Business state and evidence are written in one database transaction, so all changes commit or none do. This gives strong local atomicity but couples evidence to domain persistence. External services remain outside that transaction; an outbox still requires retry and duplicate handling.

C. An independently deployed evidence service

The controller calls a separate service with its own storage. This supports independent operation and multiple clients, but adds network ambiguity: after a timeout, the controller must use idempotency or inspection to learn whether the commit succeeded.

Choose by transaction ownership

Choose according to where the governed effect and its consistency boundary actually live.

  • Logical separation inside one application: prefer A, while accepting that it creates no independent process or security boundary.
  • Atomic business state and evidence in one database: prefer B, while accepting that evidence becomes coupled to domain persistence.
  • Shared authority across processes, teams, or zones: prefer C, while accepting that network ambiguity and service operations become product concerns.

External effects do not become transactional merely because their evidence is durable. The controller still needs idempotency or inspection before retrying an uncertain outcome.

Start with the smallest honest boundary

Start in-process when logical separation is enough. Preserve stable identities, idempotency, typed outcomes, and verifiable receipts; move to an independent service only when real isolation or multi-client needs justify its cost.

The durable principle is simple: the evidence service makes a record authoritative; the controller decides what that record permits; observability reports the execution without governing it.
